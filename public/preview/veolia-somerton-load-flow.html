Phase times — edit these

Waste categories represented in the ladder
  • Waiting. Roll-off assignment is made after the manifest is parsed. Where parsing happens on the day, the yard waits on it.

Takt and the throughput ramp

Ramp steps

Productive time of 540 minutes is an assumption: a ten-hour shift less approximately 30 minutes lunch and two breaks of about 15 minutes. Current demand of 7 trailers per day is confirmed.

Facility target as stated

  1. 9 trailers processed daily and 10 roll-offs. Today is 7 trailers and approximately 9 roll-offs. Nine trailers at ten boxes is a lower box-per-trailer ratio than today, so it depends on load composition being known before arrival, not only on working faster.
  2. Then a second dock, to double capacity and headcount. The land and buildout research covering a second Dockzilla bay is summarised in the options section.

00Drum path

Drum path

The sequence applied when the pallet carries drums, from the staging row to the empty trailer. Steps and quantities below are as stated by Somerton.

Grabber capacity2drums per lift

Step sequence

Constraints stated

  • Grabber limit. Two drums per lift. At three, one slips off.
  • Texture. A drum with no texture nests inside any drum. A textured drum does not nest inside a non-textured drum.
  • Toss to eighth position. The last drum is tossed up to stand and fall. Approximately 80% succeed; approximately 20% fall back and are re-tossed.
  • Banding. Two points per pallet: around the 2nd drum's lid channels and the 6th drum's lid channels.
  • Destination. Drum pallets return to Pomona on the empty trailer.

03Pre-read

The pre-read

Gating question, unresolved

Does the manifest packet arrive before the trailer, or does it ride in the cab? Everything in this station assumes the first. If the packet travels with the load, pre-arrival planning is not possible from this source and the station describes a future state rather than a near-term change. It gates the whole load-planning build and is the first thing to settle.

Parsing the manifest before the trailer arrives, rather than filing it on receipt. Four values from that document — weight, unit count, unit type and expected count — feed the roll-off count, the crew plan, the phase sequence and the post-unload count check. The proposed states in stations 02 and 12 depend on these values being available in advance.

Parsed fields and the decisions they feed

Pre-read calculator — one load

Type in what the parse returns and see the plan before the truck arrives. This is the arithmetic the office does at pre-verify; on the real sheet it is formulas, not typing.

Both weight inputs are blank by design. An earlier version carried a 12,000 lb box capacity and a 47% fill share chosen so that seven trailers produced nine roll-offs. That pair was back-derived from the answer, not measured, and a figure derived that way becomes a target on the yard once it is printed. It is withdrawn.

What replaces it — three measurements: (1) usable weight capacity of a roll-off, from scale tickets against box counts; (2) share of inbound weight that reaches a box, from landfill BOL weights against manifest weights; (3) registered gross and measured tare per trailer configuration. Until all three exist, the roll-off count on this page is not computed.

Document source

Manifests and cover letters are generated by company sites at the point of generation and processing, and are supplied directly. Documents produced this way carry a text layer, so search and parsing operate on text rather than on an image. Documents that arrive as scans of printed pages do not carry a text layer and would not be found or parsed by the method described here.

Conditions that affect parser output
  • Template variation. If a generating site changes its template and a label moves, the parser returns blank for that field. The code shown below returns blanks rather than substituting a value.
  • Units. Item 12 can express quantity in pounds, tons, kilograms, gallons, liters, cubic yards or cubic meters. The roll-off calculation is weight-based. Volume units require a density for the specific waste stream to convert. See the unit table in station 10.

Apps Script — pull a manifest by number 
function findManifest(manifestNo) {
  var folder = DriveApp.getFolderById(MANIFEST_FOLDER_ID);   // intake folder, not My Drive

  // 1. filename match
  var byName = folder.searchFiles(
        'title contains "' + manifestNo + '" and trashed = false');
  if (byName.hasNext()) return byName.next();

  // 2. full text - only finds it if the PDF has a text layer
  var byText = folder.searchFiles(
        'fullText contains "' + manifestNo + '" and trashed = false');
  if (byText.hasNext()) return byText.next();

  return null;   // caller must handle this - do NOT guess a file
}

function preReadFromManifest(manifestNo) {
  var file = findManifest(manifestNo);
  if (!file) {
    return {found:false, reason:"No file for " + manifestNo +
              ". Check the filename, or the document has no text layer."};
  }

  var text = extractText(file);            // see station 10 for the item map
  var lines = parseLineItems(text);        // Item 9b / 10 / 11 / 12 rows

  var units = 0, lbs = 0, unresolved = [];
  for (var i = 0; i < lines.length; i++) {
    units += lines[i].containers;
    var w = toPounds(lines[i].qty, lines[i].unit);
    if (w === null) unresolved.push(lines[i]);  // volume unit, no density
    else lbs += w;
  }

  return {
    found:      true,
    fileUrl:    file.getUrl(),
    manifestNo: pick(text, /Manifest\s+Tracking\s+Number[:\s]*([0-9]{9}\s?[A-Z]{3})/i),
    origin:     pick(text, /Generator'?s?\s+Name[^\n]*\n\s*([^\n]+)/i),
    containers: units,
    weightLb:   lbs,
    unitTypes:  tallyContainerCodes(lines),   // DM/DF -> de-lid, CF/CW -> cardboard
    lineCount:  lines.length,
    // NEVER silently drop these - they are the gallons trap
    unresolvedUnits: unresolved
  };
}

// Item 12 unit codes. Mass converts; volume does not, without a density.
var TO_LB = {P:1, T:2000, K:2.20462, M:2204.62};

function toPounds(qty, unitCode) {
  var f = TO_LB[String(unitCode).toUpperCase()];
  if (f) return qty * f;
  return null;   // G, L, Y, N - office must supply density. Do NOT assume water.
}

function pick(text, re) {
  var m = text.match(re);
  return m ? m[1].trim() : "";        // blank, never a guess
}

Behaviour of this draft: it searches one named folder rather than all of Drive; it returns null when no file matches; unmatched fields return blank rather than a substituted value; and toPounds returns null for volume units, placing those lines in unresolvedUnits for the office to complete. The patterns are fitted to the standard form, not to Somerton's documents. One manifest and one cover letter would allow them to be fitted to the actual text.

05Parse map

Manifest to form, field by field

The uniform hazardous waste manifest is a numbered federal form, so field positions are defined by item number. The tables below map those items to the fields on the entry grid. The cover letter supplies the shipment-level fields that do not appear on the manifest.

The manifest — numbered items to form fields

Mapped against the standard uniform hazardous waste manifest, EPA Form 8700-22. Verify against one of ours — item numbers are federal and stable, but our template may label them differently in the printed text.

Item 10 container codes

Each line item carries a two-letter container type code. The right-hand columns map each code to the handling phases that apply. The mapping to Somerton's unit types is provisional.

Codes DM, DF, DW and TP map to the de-lid phase. Codes CF and CW map to cardboard breakdown and travel to the baler. Codes carrying neither map to loads where both phases are skipped. This information is available from the manifest in advance of arrival.

Item 12 unit codes

Item 11 gives a quantity; Item 12 gives its unit. Four codes are mass units and convert to pounds by a fixed factor. Four are volume units and require the density of the specific waste stream to convert.

The roll-off calculation on this page is weight-based. Where a line arrives in a volume unit with no density available, the draft code returns it as unresolved rather than applying a default density. A fixed assumption of 8.34 lb/gal (water) differs from chlorinated solvents and from light hydrocarbons in opposite directions, and that difference carries through to the roll-off count.

Cover letter fields

The manifest describes the waste; the cover letter describes the shipment. Both are required to populate one trailer-load row.

Document structure: trailer, manifest, page, line

The nesting below determines the shape of the entry grid and the role of LineID.

  • A trailer carries several manifests. The cover letter states how many.
  • Each manifest has a tracking number (Item 4) and a page count (Item 2, “page 1 of N”). Additional pages are continuation sheets, form 8700-22A.
  • Each page carries several line items, Items 9b through 13. Each line is one waste stream with its own container count and quantity.
  • One line item corresponds to one row in the entry grid. ManifestID and Trailer repeat down the rows; LineID changes per row.

Two counts are available for reconciliation before unload: manifests received against the count stated on the cover letter, and pages received against “page 1 of N”. A missing continuation sheet corresponds to a waste stream present on the trailer with no accompanying paperwork.

Item 18a

The federal form contains a discrepancy block, Item 18a, for quantity, type or residue discrepancies recorded by the receiving facility. The count-variance form in station 11 records the same event. Aligning the two would produce a single record; keeping them separate would produce two.

06Variance

Count reconciliation

The expected count comes from Item 10 on the manifest. The actual count comes from the scanner after unload. The proposed flow compares the two once and records any difference, in place of repeated recounts.

Error form fields

Four fields. Manifest number, trailer, expected and actual are carried through from the pre-read and are not re-entered.

Trigger. The variance message from Telegram writes the discrepancy to the error queue. The queue opens the form at the office station with the manifest attached, rather than requiring it to be opened manually or retrieved later.

Scale of the activity

Unmeasured estimate: approximately ten minutes per recount, at two to three discrepancies on a busy day, five days a week. Both the duration and the frequency would need to be established from observation. The send-location field records where the discrepancy originated.

Yard — today's mix, bins and overtime

Set the loads coming in by type. Each type carries its own typical unit count and weight — see the table in station 14 — so the mix, not the load count, drives everything below.

Non-handling share is the portion of the shift not spent hands-on material: walking, waiting, repositioning forklifts, locating trailers, breaks, paperwork and equipment. 75% is an unmeasured estimate. 11The sheet

The entry grid

The pre-read block sits above the grid: entering a manifest number populates the fields returned by the parse. Below it, identifiers are placed in the left-hand columns, followed by expected count against actual count.

Named ranges and validation

Lists are held on PLUG_Config and referenced by name rather than entered into cells directly, so a list change is a single edit.

The Other path. Origin ends with Other — specify. Selecting it unlocks the adjacent free-text cell, which is required before submit. Other entries collect on a review list. Entries on that list are either promoted into REF_OriginCities as new origins or corrected as errors. Without a review step, entries remain on the list.

Building the submit button

  1. On PLUG_Config: Insert › Drawing, choose a beveled rectangle, type QC & SUBMIT BATCH, save and close.
  2. Drag it above the grid, clear of column A.
  3. Three dots on the drawing › Assign script › type submitBatchToMasterLog with no brackets.
  4. Test with one incomplete row. The expected result is that the whole batch is refused and the row is named.

The script writes to a historical sheet, so a defect in it affects stored records. Running it against a copy in parallel with the current process, before it writes to a live log, would surface defects without affecting stored data. The duration of any such period is open.

function submitBatchToMasterLog() {
  var ss    = SpreadsheetApp.getActiveSpreadsheet();
  var plug  = ss.getSheetByName("PLUG_Config");
  var log   = ss.getSheetByName("01_Logistics_Operations_Log");
  var ids   = plug.getRange("GRID_RowIDs").getValues();
  var range = plug.getRange("GRID_BatchInput");
  var rows  = range.getValues();
  var stamp = new Date();
  var out   = [];

  for (var i = 0; i < rows.length; i++) {
    var r = rows[i];
    var manifest = r[0], trailer = r[1], line = r[2];
    var expected = r[7], actual = r[8];

    if (!manifest && !trailer && !line) continue;      // blank row - skip

    if (!manifest || !trailer || !line) {                 // partial row - refuse the batch
      SpreadsheetApp.getUi().alert(
        "BATCH REJECTED at sheet row " + (i + 4) + ".\n\n" +
        "ManifestID, Trailer Number and LineID must all be filled.\n" +
        "Nothing has been saved. Fix the row and submit again.");
      return;
    }

    // variance is recorded, never blocked - the load still gets logged
    if (expected !== "" && actual !== "" && expected != actual) {
      queueCountError(manifest, trailer, expected, actual);
    }
    out.push([stamp, ids[i][0]].concat(r));
  }

  if (!out.length) {
    SpreadsheetApp.getUi().alert("Nothing to submit - the grid is empty.");
    return;
  }

  // one write, not one per row
  log.getRange(log.getLastRow() + 1, 1, out.length, out[0].length).setValues(out);
  SpreadsheetApp.flush();
  range.clearContent();
  SpreadsheetApp.getUi().alert(out.length + " lines logged.");
}

Behaviour of this draft: every row is validated before any row is written, so a batch containing an incomplete row commits nothing. The write is a single setValues call rather than a loop of appendRow, so concurrent submissions do not interleave. A count variance queues an error entry and does not reject the row.

Handoff windows

Four times a day. The yard is off the clock on breaks — nobody reports during one. These are the moments immediately before or after.

Data ownership. The yard reports values, the bot returns them as text, and the office confirms them before submission. Accountability for entered data sits with the office. The read-back places the confirmation step at the point of reporting.

Shared Drive, not the desktop

Five folders, three or four levels deep at most. Nothing operational lives on a C: drive, a desktop, or a Downloads folder — after the network merge on 2027-01-01, anything outside the Shared Drive is invisible to everyone who needs it, and the auto-pull cannot see it either.

File names

[YYYYMMDD]_[Department]_[AssetType]

  • 20270105_LogisticsOperations_InboundMaster
  • 20270105_YardManagement_ShiftLog_0600
  • 20270105_MAN-8804_Manifest — manifests carry the number, because that is how the auto-pull finds them

No status suffix. No _FINAL, _v2 or _ACTIVE. Folder location carries status instead: a live file sits in 01_Logistics_Operations, a closed week moves to _Archive. Change history is available under File › Version history.

Starting a new day's sheet

Renaming an open template renames that file rather than creating a new one, which removes the template. The workflow below creates a copy instead.

  1. The Coordinator publishes the template as a force-copy link: take the normal sharing URL and replace everything from /edit onward with /template/preview.
  2. You click the link and press Use template. Google makes you a brand-new file. The master is untouched.
  3. Rename it to [YYYYMMDD]_LogisticsOperations_InboundMaster.
  4. Click the folder icon beside the name › Shared drives › 01_Logistics_Operations › Move. Copies are created in the user's own My Drive; until moved, the file is not visible to other users or to the script.

File › Download produces a local copy that is not visible to other users and does not receive subsequent changes.
